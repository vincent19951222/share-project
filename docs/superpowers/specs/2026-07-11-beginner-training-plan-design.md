# 新手四周训练计划设计

**日期：** 2026-07-11

**状态：** 产品设计已确认，待用户审阅文档后进入实施计划

**适用项目：** 脱脂牛马（share-project）

## 1. 背景

当前健身打卡能够记录训练类型、训练部位和训练时长，但主要回答“今天练了什么”，无法回答新手更核心的问题：“我今天应该练什么”。

本设计新增一套面向减脂健身新手的四周训练计划。它不是第五个主导航，也不是新的泛化记录维度，而是现有“健身打卡”的行动指导层。

第一版不使用 LLM，不做动态重排。用户开始计划后，每个日期的安排保持固定；某天未完成只记为错过，不影响后续日期。

## 2. 产品目标

第一版需要帮助“想减脂、缺少训练方法、不知道今天练什么”的健身新手完成以下闭环：

1. 用少量信息建立训练偏好。
2. 获得一套适合自己的固定四周入门计划。
3. 每天快速看到训练内容。
4. 按动作完成训练，并复用现有健身打卡保存结果。
5. 清晰区分已完成、今日待练、休息日和已错过。

## 3. 非目标

第一版明确不包含：

- LLM 生成、解释或调整训练计划。
- 自动顺延、补课或根据疲劳重新排期。
- AI 健身教练对话。
- 饮食计划或热量处方。
- 伤病诊断、康复方案或医疗建议。
- 团队挑战和团队共同任务。
- 个人成长档案独立页面。
- 允许用户从全部动作中自由编排计划。
- 动作图片和 GIF 的直接迁移。
- 对个人菜单中的 AI 生图入口做任何调整。

团队挑战、AI 教练和动态计划属于后续独立阶段，不应阻塞第一版。

## 4. 目标用户与训练场景

### 4.1 目标用户

- 健身经验较少。
- 主要目标是减脂、建立运动习惯和提升基础体能。
- 不熟悉动作编排、训练频率和组次安排。
- 希望系统直接告诉自己当天做什么，而不是提供复杂的专业工具。

第一版不以进阶健美、力量举、专项运动表现或康复人群为主要服务对象。

### 4.2 训练场景

- 主计划以健身房器械和常见自由重量为主。
- 每个主要器械动作提供一个居家或徒手替代。
- 用户可以在没有去健身房时自行采用替代动作，但替换不会触发计划重排。

## 5. 核心产品决策

### 5.1 固定四周周期

用户创建计划时一次获得完整四周内容。界面以当前周为主，但允许查看整个周期。

- 第 1 周：熟悉动作和训练节奏。
- 第 2 周：保持动作结构，适当增加次数。
- 第 3 周：增加少量训练量。
- 第 4 周：巩固完成，不安排极限测试。

四周之间只做固定模板内预先设计的轻量递进，不读取用户反馈自动调整。

### 5.2 日期独立

计划生成后，每个训练日与具体日期绑定。

- 周一未完成，周一在日期结束后显示“已错过”。
- 周二仍执行原定周二内容。
- 不补课、不顺延、不交换训练日。
- 未完成某天不会改变本周或下周内容。
- 过去日期的“已错过”由日期和完成记录计算，不依赖定时任务。

### 5.3 用户决定训练日期

用户先选择每周训练次数和通常可以训练的星期，系统只负责给这些日期匹配训练内容。

非训练日显示休息状态，并提示下一次训练日期。

## 6. 模板方案

第一版采用固定模板矩阵，不使用统一计划，也不使用实时动作拼装算法。

### 6.1 匹配维度

- 每周训练次数：2 天、3 天、4 天。
- 单次训练时长：30 分钟、45 分钟、60 分钟。
- 训练日期：由用户选择。
- 主要场景：健身房。
- 替代场景：居家或徒手动作。

共形成 9 套基础组合。每套组合包含完整四周内容。

### 6.2 模板来源与版本

- 模板以项目内版本化 JSON 作为内容源。
- 每份模板具有稳定标识和版本号。
- 模板必须通过结构校验后才能进入产品。
- 创建用户计划时复制完整内容形成快照。
- 后续修改模板只影响新创建的计划，不修改进行中的用户计划。

第一版不提供后台模板编辑器。模板变更随代码评审和版本发布完成。

## 7. 用户流程

### 7.1 入口

不增加第五个主导航。训练计划直接进入现有“健身打卡”页面。

在团队信息与打卡表格之间增加紧凑的“今日计划”卡：

- 未创建计划：显示“生成我的 4 周计划”。
- 训练日未完成：显示训练主题、预计时长和动作数量。
- 训练日已完成：显示完成状态。
- 训练日已过去且未完成：显示“已错过”。
- 休息日：显示“今日休息”和下一次训练日期。

每周总览和四周总览放在计划详情中，不占用主导航。

### 7.2 首次创建

创建流程只收集匹配模板所需的信息：

1. 每周训练 2、3 或 4 天。
2. 具体训练星期。
3. 单次训练 30、45 或 60 分钟。
4. 可用器械条件。
5. 需要避开的身体部位或动作类型。

第一版不要求年龄、性别、身高、体重和体脂等与模板匹配没有直接关系的信息。

系统根据输入匹配模板，展示计划摘要并由用户确认开始。用户同时只能拥有一个进行中的四周计划。

### 7.3 今日训练

训练日详情按以下顺序展示：

1. 热身，约 3 至 8 分钟。
2. 主训练，约 4 至 7 个动作。
3. 可选有氧，根据模板安排。
4. 放松和简短注意事项。

每个动作展示：

- 中文动作名称。
- 训练部位。
- 组数、次数或持续时间。
- 组间休息时间。
- 简短动作要点。
- 健身房动作对应的居家替代。
- 面向新手的重量选择提示。

用户可以逐项勾选动作。实际重量和完成次数为可选信息，不要求逐组填写。

### 7.4 完成与打卡

训练计划不能建立第二套奖励或打卡结算。

- 用户尚未完成今日健身打卡时，完成今日计划会生成训练记录并完成现有健身打卡。
- 用户已经完成今日健身打卡时，完成计划只更新今日训练明细，不重复发放奖励。
- 重复请求必须保持幂等，不得创建重复训练记录或重复奖励。
- 撤销现有健身打卡时，需要同步清理计划完成关联，或在界面中明确阻止会产生矛盾状态的操作。

## 8. 训练内容结构

### 8.1 动作库范围

参考数据源：[hasaneyldrm/exercises-dataset](https://github.com/hasaneyldrm/exercises-dataset)。

第一版从外部数据集中筛选约 100 至 150 个适合新手的动作，不向用户直接开放全部 1324 个动作。

可迁移的原始字段包括：

- 外部稳定 ID。
- 英文名称和中文展示名称。
- 身体部位。
- 主要目标肌肉和辅助肌肉。
- 器械类型。
- 中文动作说明。

产品需要额外维护：

- 新手难度。
- 动作模式。
- 默认组数、次数和休息时间。
- 适用模板。
- 居家替代动作。
- 避开部位和限制标签。
- 面向新手的简短动作提示。

### 8.2 媒体授权边界

外部仓库的代码、数据结构和说明文本采用 MIT 许可，但图片和 GIF 属于 Gym Visual，并受独立媒体条款约束。

第一版只迁移经过确认可使用的结构化数据和文本，不迁移仓库中的图片与 GIF。后续若需要动作媒体，必须单独完成授权确认或制作自有素材。

线上系统不依赖 GitHub 仓库运行。数据只在开发阶段通过导入流程进入项目。

## 9. 系统边界

系统分为五个职责单一的部分：

### 9.1 动作目录

保存筛选后的标准动作、展示内容和产品补充标签。动作目录不负责生成用户计划。

### 9.2 模板目录

保存 9 套基础组合及其四周内容。模板只引用动作目录中的稳定动作标识。

### 9.3 用户训练档案

保存模板匹配所需的训练频率、具体星期、单次时长、器械和避开项。

### 9.4 用户计划快照

保存创建时的模板版本和完整四周内容。用户日计划读取快照，而不是实时读取当前模板。

### 9.5 完成记录

保存计划日完成时间、动作勾选结果以及可选的实际重量和次数，并关联现有训练记录与健身打卡。

## 10. 数据流

### 10.1 内容准备

```text
外部动作数据
→ 导入与字段标准化
→ 人工筛选新手动作
→ 补充产品规则字段
→ 校验动作目录
→ 模板引用动作目录
```

### 10.2 创建计划

```text
用户填写训练档案
→ 匹配训练次数和时长模板
→ 映射用户选择的星期
→ 校验避开项和动作可用性
→ 创建连续四周的计划快照
→ 返回当前周和今日状态
```

### 10.3 完成计划

```text
用户勾选并完成今日计划
→ 校验计划日属于当前用户和当前日期
→ 幂等保存完成记录
→ 调用现有健身打卡与训练记录逻辑
→ 返回更新后的计划和打卡状态
```

## 11. 异常与边界处理

- 找不到匹配模板时不创建计划，提示用户调整训练次数、时长或器械条件。
- 模板引用不存在的动作时，模板校验失败，不允许发布。
- 用户存在进行中计划时，不允许直接创建第二个计划。
- 过去未完成的训练日只读展示为“已错过”，不能补做后改变原日期状态。
- 未来训练日不能提前标记完成。
- 重复提交完成操作不能重复创建记录或发放奖励。
- 训练计划接口失败不能破坏现有健身打卡页面的可用性。
- 外部动作数据导入失败不能影响线上运行。
- 用户选择避开某部位后，没有安全可用模板时不做猜测性推荐。

## 12. 测试与验收

### 12.1 内容校验

- 9 种模板组合全部存在。
- 每套模板包含完整四周。
- 模板引用的动作全部存在。
- 每个主动作都有居家替代或明确标记无替代。
- 每个动作包含必要的组次、休息和提示字段。
- 模板时长与目标档位基本一致。

### 12.2 计划生成

- 2、3、4 天训练频率均能正确匹配模板。
- 30、45、60 分钟均能正确匹配模板。
- 用户星期选择能正确映射到连续四周的实际日期。
- 跨月、跨年和时区边界正确。
- 创建后修改模板不会改变用户快照。
- 同一用户不能同时创建两个进行中计划。

### 12.3 日期状态

- 今日训练正确显示待完成或已完成。
- 非训练日正确显示休息状态。
- 过去未完成日期显示已错过。
- 周一错过后，周二至周日计划内容和日期保持不变。
- 不依赖定时任务也能正确计算已错过状态。

### 12.4 打卡集成

- 未打卡用户完成计划后只产生一次有效打卡和奖励。
- 已打卡用户完成计划后只更新训练明细。
- 重复提交不会重复发奖励。
- 撤销打卡不会留下矛盾的计划完成状态。
- 计划接口异常时现有打卡功能仍可使用。

## 13. 发布范围建议

第一版建议拆成三个可独立验收的交付阶段，但属于同一产品版本：

1. 动作目录与模板内容基础：完成数据筛选、产品字段、9 套模板及校验。
2. 四周计划创建与查看：完成用户训练档案、模板匹配、快照和今日计划卡。
3. 训练执行与现有打卡集成：完成动作勾选、完成记录、训练明细和幂等奖励衔接。

本设计不把 AI、动态调整或团队挑战预埋成第一版必须实现的抽象。后续需要这些能力时，再以独立设计扩展稳定的数据边界。

## 14. 成功标准

第一版上线后的核心判断不是动作数量，而是新手是否真正开始使用计划：

- 完成训练档案并成功创建计划的用户比例。
- 创建计划后七天内至少完成一次计划训练的用户比例。
- 四周周期内实际开始过训练的周数。
- 今日计划打开后完成健身打卡的转化率。
- 因计划功能导致的重复打卡、重复奖励和矛盾状态数量为零。

个人成长档案可以在计划和训练数据积累后，以这些真实数据为基础自然生成，不在第一版提前建设空洞页面。
